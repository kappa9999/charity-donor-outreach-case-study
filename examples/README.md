# Executable examples

The repository includes two deterministic, reviewer-facing datasets. Both run through the same
public CLI, policy engine, provider boundary, draft guard, and output contract used by the tests.
Neither path sends outreach.

## Run everything

From the repository root after installation:

```bash
python scripts/run_examples.py --output-dir out/reviewer-demo
```

The command verifies fixture provenance, executes both datasets, compares every generated byte to
the committed golden outputs, prints one JSON summary, and writes
`out/reviewer-demo/reviewer-summary.md` with readable representative drafts.

| Dataset | Records | Expected dispositions |
| --- | ---: | --- |
| `realistic-controls` | 6 | 2 draft-ready, 1 review-required, 1 blocked, 2 suppressed |
| `jll-supplied-table` | 50 | 33 draft-ready, 17 review-required |

## JLL-supplied sample provenance

The received `charity-donor-outreach.zip` is 5,495 bytes with SHA-256
`08833833da105c65242643ed07049c7debd931f9bbfd348690831c49f8d64f5b`. Its only substantive
file is the original `SKILL.md`, which embeds a 50-row mocked donor table.

[`jll-supplied/source-donors.csv`](jll-supplied/source-donors.csv) is a lossless normalized
transcription of that table. Every supplied field has the same value; the CSV adds only stable row
IDs and split first/last-name columns for deterministic processing. A mechanical field-by-field
comparison against the attachment found zero differences across all 50 rows.
[`jll-supplied/fixture-manifest.json`](jll-supplied/fixture-manifest.json) records the attachment
identity, locked source and derived hashes, row count, columns, and field lineage. Run the
reproducibility check directly with:

```bash
python scripts/build_jll_fixture.py --check
```

The supplied table does **not** include channel consent, suppression status, a contact path,
last-contact date, an exact last-gift date, campaign controls, or approved outreach claims. A safe
implementation cannot silently infer those values. The executable operational fixture therefore:

- preserves the supplied identifiers, names, gift values, totals, and tier information;
- derives last-gift amount from the final supplied history entry and segment from supplied tier;
- uses December 31 as an explicitly labelled test-only placeholder for the supplied gift year;
- adds visibly labelled synthetic test controls for consent, suppression, email, and contact date;
- omits region and volunteer status from drafting context; and
- uses a hypothetical organization/campaign with reserved `example.org` contact endpoints.

Those additions prove how all 50 provided rows behave once authoritative operational controls are
present. They are not claims that JLL supplied consent or that the placeholder dates are real.
Production onboarding must join those fields from authoritative systems before generation.

## Additional realistic controls

The compact root fixture exercises common day-to-day outcomes that an operator needs to
understand before using the batch workflow:

| Donor | Scenario | Expected result |
| --- | --- | --- |
| SYN-001 | Granted email permission and one approved history fact | draft-ready |
| SYN-002 | Permission not established | blocked without provider call |
| SYN-003 | Explicit do-not-contact | suppressed without provider call |
| SYN-004 | Relationship-managed/high-value donor | review-required |
| SYN-005 | Complete postal-letter path | draft-ready |
| SYN-006 | Contacted inside the campaign frequency window | suppressed without provider call |

The broader automated suite adds denied permission, missing contacts, malformed records, unsafe
facts, provider failures and mutations, batch continuation, output rollback, resource ceilings,
and adversarial privacy/quality cases. See [quality evidence](../docs/QUALITY.md).
